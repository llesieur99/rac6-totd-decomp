# The function catalogue

The retail executable is stripped, so the project has no symbol table to
start from. The catalogue is the project's own answer to "where are the
functions?", and it is built from evidence: every address in it carries the
reason why it is there.

The catalogue lives in [`config/functions.tsv`](../config/functions.tsv) and
is generated by [`tools/ppu_funcs.py`](../tools/ppu_funcs.py) and
[`tools/ppu_bounds.py`](../tools/ppu_bounds.py). It holds research
metadata only - addresses and the evidence for them - never game bytes.

## The truth the executable keeps

The PlayStation 3's loader does not jump to the program's code: the entry
point of the executable is the **module descriptor**, a table of
`(function address, global pointer)` pairs that names what every linked
module exports.  On the target it holds **24,069 entries for 24,069
distinct function addresses** - the retail build's own list of its
functions, which survives the strip.

There is a second table, the **official procedure descriptor**, which holds
**8,153 procedures** on this target.  The two are not the same table and
they are not the same size: a module only exports what it exports, and
this game's own modules export more of their functions than the procedure
descriptor records.  For the sibling project on *A Crack in Time* the two
were almost the same size (34,482 and 68,490 entries); here they are not,
and the **module descriptor is the larger and the better reference**.

That list is the reference every method is measured against.

## The methods

### The module descriptor (the truth)

`tools/ppu_modules.py` reads the table at the entry point:

```sh
python tools/ppu_modules.py work/eboot/EBOOT.elf
```

```
module descriptor at 0x874050: 24069 functions
  1748 link units, the largest ones holding 1009, 933, 582, 482, 479, 475, 446, 435 functions
  3 distinct TOC bases
  7 runs of entries sharing a TOC base, the largest holding 8455, 8151, 7193, 235 functions
```

The table says two useful things: where the functions are, and which
functions were **linked together** - the grouping into translation units
that the compiler reacts to (see [ABI.md](ABI.md)).

### The prologue scan

The PS3 SDK's PPU functions open with a fixed shape: the frame is set up
with `stdu r1, -N(r1)` and the link register is saved with `mflr rX`. The
two instructions appear in both orders, and the frame size varies, so the
scanner matches the instruction words, not a fixed byte sequence.

The scan is cheap and it has no false negative on a function that follows
the SDK's shape, but it has false positives, and they are systematic: the
SDK writes the frame setup before *or* after the `mflr`, so a scan that
accepts either order also accepts the **second instruction of a function**.

The link register is saved in **any** general register, so the scan has to
match all of them: a mask that only clears the low three bits of the
register field misses the functions that keep the link register in `r8` or
above.

### The call scan

Every `bl` names an address the program calls. The scan collects the
targets, which gives a second opinion about where the functions are - and
it also shows its own weakness: the compiler generates calls to *blocks*
inside a function (shared epilogues, jump-table targets), so a call target
is not necessarily a function start.

### The flow bounds (the third method)

`tools/ppu_bounds.py functions` recovers the boundaries from the **control
flow** instead of from the opening of the function.  It walks from the
entry point, the call targets and the first instruction of the code,
stops on the terminals (`blr`, `beqlr`, a sibling branch to a known
function or over another function's opening, the cases of an inline jump
table), and ends a walk when it reaches an address another function
already owns.  The prologue is never used to *find* a function - only read
afterwards, to describe a boundary the flow has already delimited.

## What is published

`config/functions.tsv` holds the addresses the executable itself confirms:

| Column | Meaning |
|---|---|
| `address` | the function's address in the executable |
| `kind` | the methods that found it |
| `evidence` | `all` when more than one method agrees, `descriptor` when the descriptor alone confirms it |

## The counts on the pinned target

| Set | Count |
|---|---|
| **module descriptor (the truth)** | **24,069** |
| official procedure descriptor | 8,153 |
| flow bounds | 21,728 |
| prologue candidates | 14,504 |
| distinct call targets | 11,073 |
| the two cheap methods together | 4,306 |
| the merged catalogue | 28,640 |
| **the published catalogue** | **22,212** |

The published catalogue is the merged catalogue restricted to the
addresses the module descriptor confirms: 22,212 of the descriptor's
24,069 addresses, of which 13,522 are seen by more than one method and
8,690 by the descriptor alone.

## The methods measured against the truth

On the target, with the module descriptor as the reference
(`python tools/ppu_bounds.py evaluate <eboot.elf> --truth <file>`):

| method | found | correct | false | missed | precision | recall |
|---|---|---|---|---|---|---|
| prologue scan | 14,504 | 10,665 | 3,839 | 13,404 | 73.5 % | 44.3 % |
| call scan | 11,072 | 8,561 | 2,511 | 15,508 | 77.3 % | 35.6 % |
| prologue + call | 4,306 | 4,304 | 2 | 19,765 | **100.0 %** | 17.9 % |
| prologue \| call | 21,270 | 14,922 | 6,348 | 9,147 | 70.2 % | 62.0 % |
| **flow bounds** | 21,728 | 19,260 | 2,468 | 4,809 | 88.6 % | **80.0 %** |

The two cheap methods together are **exact** on this target - the 4,304
addresses they both see are all real functions, with two exceptions.

The flow method is the one that finds most of the functions, and it is
the one the published catalogue is built on.

### A warning about the reference

The module descriptor is *not* a complete list: a module only exports
what it exports. That is why the prologue scan's "false positives" are
3,839 and not the 2,299 of the sibling project - most of them are real
functions that the descriptor simply does not name. The engine's own
initialisation function at `0x10210` is one of them: it is a function,
and the descriptor does not list it.

This is the reason the reference and the method have to be read together,
and the reason the flow method (which does not use the descriptor at all)
is the one that finds the functions the descriptor misses.

## The three opinions, and what they say

| Set | Addresses | How it is obtained |
|---|---|---|
| the two cheap methods | 4,306 | the prologue and the call scan agree |
| the flow method | 21,728 | the control flow delimits the functions |
| the executable's own list | 24,069 | the module descriptor at the entry point |

Comparing the flow method with the two cheap methods against the published
catalogue of 4,646 addresses:

```
functions found   : 21728
catalogue         : 4646
  confirmed       : 4609
  invalidated     : 12
  not covered     : 25
new functions     : 17119
catalogue lost    : 37
```

Twelve addresses of the cheap catalogue are not functions, and 17,119
addresses the flow method found are not in it. That is the size of the
gap the two cheap methods leave, and it is why the catalogue is built on
the third.

## What is still missing

The flow method misses the functions that follow a call that never
returns, and the cases of jump tables that are written in memory rather
than inline. Both are known, bounded and measured in the sibling project
on the same kind of executable, and both are open here too.
